# CreamBuffet Server

This is the dedicated Godot 4.6 headless server for CreamBuffet online play. It
uses Godot ENet transport with UTF-8 JSON packets and runs as a separate Godot
project from the client.

## Current Scope

- Headless Godot server project.
- ENet server listening on UDP, default port `7000`.
- JSON protocol version `1`.
- Lobby/session flow: welcome, public room list, create room, join room,
  leave room, host start, disconnect cleanup.
- Room IDs are 6-character uppercase codes generated by the server.
- Rooms support 1 to 4 players.
- The active map list comes from `data/game_catalog.json`.
- The current `beginner` map has 10 levels.
- Match state is server-authoritative for keys, doors, goals, hazards,
  button state, linked object state, push-box validation/control, and level
  transitions.

`world_count` and `randomized` are accepted by the room creation payload for
client UI compatibility, but the current server builds the playable level list
from the selected catalog map.

```text

```

## Run Locally

From the repository root:

```bash
godot --headless --path server
```

Optional runtime variables:

```text
CREAMBUFFET_SERVER_PORT
CREAMBUFFET_SERVER_MAX_CLIENTS
CREAMBUFFET_SERVER_EXIT_AFTER_MS
```

Example smoke test:

```bash
CREAMBUFFET_SERVER_EXIT_AFTER_MS=3000 godot --headless --path server
```

On PowerShell, set the variable first:

```powershell
$env:CREAMBUFFET_SERVER_EXIT_AFTER_MS = "3000"
godot --headless --path .\server
```

## Run With Docker

From the repository root:

```bash
cp .env.example .env
docker compose up --build
```

Manual Docker commands:

```bash
docker build -t creambuffet-server .
docker run --rm --env-file .env -p 7000:7000/udp --name creambuffet-server creambuffet-server
```

The Dockerfile downloads the Godot Linux binary, copies the `server/` project
into the runtime image, runs as the non-root `godot` user, and supports Docker
`amd64` and `arm64` builds.

## Packet Format

Packets are reliable ENet messages unless a route explicitly uses unreliable
ordered delivery. Packet payloads are UTF-8 JSON objects. The maximum accepted
packet size is `16384` bytes.

Current packets should include protocol version `v=1`:

```json
{
  "v": 1,
  "type": "create_room",
  "request_id": "create_room-1",
  "payload": {
    "player_name": "Host",
    "visibility": "public",
    "max_players": 4,
    "map_id": "beginner",
    "world_count": 10,
    "randomized": false
  }
}
```

The legacy `world_event_request` route is still accepted for old clients. New
client code should send `world_action_request`.

## Client Message Types

Accepted by `server_main.gd`:

```text
hello
ping
list_rooms
create_room
join_room
leave_room
start_match
player_state
level_changed
level_complete
world_event_request
world_action_request
```

`level_changed` and `level_complete` are intentionally rejected because level
transition is server-authoritative.

## Server Message Types

Sent by the server:

```text
welcome
pong
room_list
room_created
room_joined
room_left
room_updated
match_started
player_state
pushable_control
level_transition
world_event
error
```

Room snapshots include `match_state` while a match is active. Clients use that
snapshot to restore object state when entering or changing levels.

## Server-Authoritative Mechanics

`MatchState` validates world actions against `data/game_catalog.json` and the
last known player runtime state. Current handlers:

```text
key_door.collect
key_door.open
goal.enter
goal.exit
hazard_respawn.player_death
push_box.state
button_platform.button_state
```

Broadcast world event kinds include:

```text
key_collected
door_opened
goal_entered
goal_exited
player_died
player_respawned
button_state
push_box_state
object_state_changed
```

Push boxes are not fully simulated by the server. The server validates nearby
client observations and push intents, stores the accepted position, and
broadcasts aggregate `pushable_control` data plus accepted state events.

## Catalog Rules

The server catalog defines:

- Maps and their ordered level IDs.
- Level scene paths used by the client.
- Spawn points.
- Map-level default rulesets plus level overrides.
- Optional player-state defaults that seed match runtime state.
- Network object definitions and trigger/body shapes.
- Completion rules.
- Linked object state changes, such as buttons activating moving platforms.

When a room is created, the server validates that every level in the selected
map only uses allowed and known rulesets and object kinds.
